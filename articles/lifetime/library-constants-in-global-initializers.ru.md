# Константы библиотеки пусты или роняют программу в инициализаторах и деструкторах глобальных объектов

[English](library-constants-in-global-initializers.md) | **Русский**

Класс задач: C++-библиотека с публичными константами классового типа (`static const CandleType MINUTE;`, определённой
в `.cpp`) или картами констант, и код пользователя с глобальными переменными: синглтонами, реестрами, конфигурацией,
фикстурами тестов.

Примеры и ссылки — в разделе [«Где встречалось»](#где-встречалось).

## Симптомы

- В инициализаторе глобальной переменной `Lib::CONSTANT.getName()` возвращает пустую строку, `parse("h")` ничего не
  находит или падает; тот же вызов в `main()` работает.
- Падает со статической библиотекой и работает с динамической или меняется от порядка линковки.
- На выходе падает деструктор глобальной переменной, использующий константу: `pure virtual function call` (MSVC
  R6025, libstdc++ `pure virtual method called`) или чтение освобождённой памяти.
- ASan с `check_initialization_order=1` сообщает `initialization-order-fiasco`.

## Причины

1. **Порядок динамической инициализации между единицами трансляции не определён.** Константа, чей конструктор не
   `constexpr` (член `std::string`, `std::function`, карта), инициализируется динамически, и единица трансляции
   пользователя может оказаться первой. Со статической библиотекой объектные файлы архива — просто ещё несколько
   единиц трансляции исполняемого файла. Динамическую библиотеку загрузчик обычно инициализирует раньше зависящего от
   неё кода, поэтому там проблема прячется.
2. **До динамической инициализации объект заполнен нулями.** Для `std::string` это даже не корректная пустая строка:
   чтение может упасть, а не просто вернуть `""`.
3. **Разрушение идёт в порядке, обратном созданию.** Глобальный объект пользователя, созданный раньше константы,
   разрушается после неё. Во время разрушения, а на практике и после него, таблица виртуальных функций объекта —
   базового класса, и виртуальный вызов заканчивается вызовом чисто виртуальной функции. Константа с нетривиальным
   деструктором (`std::string`, `std::shared_ptr`, виртуальный деструктор) разрушается на выходе, даже если её
   инициализация константная.
4. **Константа, скопированная из другой константы, — динамическая.** `DEFAULT = LAST` читает переменную, а
   `constinit`-переменная (не `constexpr`) не годится для константных выражений. GCC 13 такое чтение принимал, Clang 18
   и MSVC 19.42 отвергали: сборка, зелёная только на GCC, ничего не доказывает.

## Рецепт

1. **Сделать константы константно инициализируемыми и поручить проверку компилятору.** Литеральные типы
   (`std::string_view` на литерал вместо `std::string`), `constexpr`-конструкторы и `constinit` в определении: если
   инициализация не константная, сборка падает. Объявления в заголовках и имена можно не менять.

   ```cpp
   // заголовок
   class CandleType {
       std::string_view name_;
   public:
       constexpr explicit CandleType(std::string_view name) noexcept : name_(name) {}
       static const CandleType MINUTE;
   };

   // .cpp
   constinit const CandleType CandleType::MINUTE{"m"};
   static_assert(std::is_trivially_destructible_v<CandleType>);
   ```

2. **Сделать их тривиально разрушаемыми**: без виртуального деструктора, без членов `std::string` и
   `std::shared_ptr`. Тогда на выходе для них ничего не выполняется, и деструктор кода пользователя может ими
   пользоваться. Базовый класс, который должен остаться полиморфным, получает защищённый невиртуальный деструктор, а
   наследники — `final`.
3. **Производные константы строить из тех же литералов** через `constexpr`-фабрику, а не копированием другой
   константы.
4. **Реестры констант — `constinit std::array` плюс `std::span`** вместо `std::unordered_map`; линейного поиска по
   нескольким десяткам элементов хватает.
5. **То, что не может быть константой** (куча, хендлы рантайма): создавать при первом обращении в статике внутри
   функции, а если оно нужно на выходе — не разрушать никогда (`static T &x = *new T(...)`, `absl::NoDestructor`).
   Ленивый хендл — указатель на функцию плюс `std::once_flag` вместо `std::function`.
6. **MSVC и экспорт из DLL**: явная специализация статического члена данных шаблона класса — это определение, поэтому
   `__declspec(dllimport)` на ней запрещён (C2491). Такие константы объявляются в каждом классе-наследнике, а не в
   шаблоне.

## Чего это стоит

- Геттеры, возвращавшие `const std::string &`, возвращают `std::string` или `std::string_view`: меняется ABI, а член
  `const std::string &`, хранивший результат, повисает.
- Ключи, ставшие `static constexpr char[]`, сравниваются с `const char *` по указателю, а `KEY + "x"` больше не
  компилируется.
- Карты констант меняют тип: код, который называет `std::unordered_map<...>`, ломается.

## Как тестировать

- Тестовый исполняемый файл, чьи глобальные инициализаторы читают каждую константу и вызывают использующие их функции
  (`parse`, `valueOf`), слинкованный со статической библиотекой. Печатать имя перед чтением, чтобы падение называло
  константу, и сравнивать со значениями, прочитанными в `main()`.
- То же для деструкторов: глобальный объект, чей деструктор читает константы.
- ASan под Linux: `ASAN_OPTIONS=check_initialization_order=1:strict_init_order=1`.
- Собирать Clang и MSVC, не только GCC (причина 4).
- Красная проверка: вернуть одной константе `std::string` или убрать `constinit` — падает тест или сборка.

## Чек-лист для ревью

- [ ] Новая публичная константа — литеральный тип с `constexpr`-конструктором и `constinit`-определением.
- [ ] `static_assert(std::is_trivially_destructible_v<T>)` для типов констант.
- [ ] Ни одна константа не копируется из другой.
- [ ] Нет `std::string`, `std::function`, карт и `std::shared_ptr` в области видимости пространства имён на пути
      `parse`/`valueOf`.
- [ ] Тест статической инициализации покрывает новую константу.

## Где встречалось

- **dxFeed Graal C++ API** — `CandleType::parse("h")` в инициализаторе глобальной переменной падал со статической
  библиотекой; виртуальный вызов на константе атрибута свечи в деструкторе глобального объекта мог вызвать чисто
  виртуальную функцию. Константы стали `constinit`-литеральными типами, карты — `ConstantMap` поверх массивов,
  атрибуты — тривиально разрушаемыми; тест статической инициализации читает их все из глобальных инициализаторов:
  [#143](https://github.com/dxFeed/dxfeed-graal-cxx-api/pull/143),
  [#144](https://github.com/dxFeed/dxfeed-graal-cxx-api/pull/144).
- **btop** — глобальный объект одного файла инициализируется глобальным объектом другого; программа падает до
  `main()` примерно в половине сборок, в зависимости от компилятора и линковщика (Clang, mold):
  [aristocratos/btop#1748](https://github.com/aristocratos/btop/issues/1748).
- **GCC** — с `-flto` `extern const std::string` из другой единицы трансляции инициализировалась после статического
  члена класса, который её читал. Отчёт закрыт как invalid: порядок между единицами трансляции не определён, и опция
  компилятора вправе его поменять: [GCC bug 105876](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=105876).

## Открытые вопросы
