# Из кода, записанного через оболочку, пропадают обратные слеши

[English](backslashes-lost-on-the-way-through-a-shell.md) | **Русский**

Исходный код, регулярные выражения и пути Windows, которые пишут в файл или передают командой через оболочку:
скриптом, инструментом оболочки ИИ-агента или однострочником. Каждый слой на этом пути может счесть `\` началом
escape-последовательности и съесть один слеш из двух.

Примеры и ссылки — в разделе [«Где встречалось»](#где-встречалось).

## Симптомы

- `if (c == '\\')` приходит как `if (c == '\')`: `missing terminating ' character`, сборка падает.
- `std::regex("\\d")` приходит как `std::regex("\d")`: только предупреждение `unknown escape sequence: '\d'`, а
  шаблон теперь совпадает с буквой `d`.
- Heredoc с разделителем в кавычках (`<<'EOF'`), который bash не трогает, всё равно теряет каждый второй слеш.
- `\n` в формате превращается в `n`, `C:\x\y` в `C:xy`.

## Причины

1. **Git Bash сам разбирает свою командную строку Windows.** Программа Windows, которая запускает Git Bash как
   `bash.exe -c "<скрипт>"`, передаёт скрипт одним аргументом в кавычках. Среда выполнения MSYS2 сама делит
   командную строку на аргументы и внутри аргумента в кавычках превращает `\\` в `\` ещё до того, как скрипт увидит
   bash; поэтому heredoc в кавычках не спасает. Аргумент без пробелов не берётся в кавычки и доходит целым.
   Программы, которые следуют правилам Microsoft (`wsl.exe`, `python.exe`), сохраняют `\\`. Под удар попадают:
   - инструменты оболочки ИИ-агентов в Windows, которые выполняют команды через Git Bash (замечено у инструмента
     Bash в Claude Code; инструменты Write, Edit и PowerShell того же агента сохраняют байты);
   - `subprocess.run(["bash", "-c", script])` в Python, `& bash.exe -c "..."` в PowerShell.
2. **Bash и сам во многих местах считает `\` экранирующим символом:**
   - heredoc без кавычек (`<<EOF`) и двойные кавычки: `\\` → `\`;
   - `echo -e` и строка формата `printf`: `\\` → `\`, `\n` → перевод строки;
   - `read` без `-r`: `\\` → `\`, одиночный `\` удаляется;
   - замена в `sed s/…/…/`: `\\` → `\`, и подставленная в неё переменная разбирается так же;
   - путь Windows без кавычек: `C:\x\y` → `C:xy`.
3. **По пути встречается строковый литерал другого языка.** Код, завёрнутый для записи в строку Python, JSON или
   C, теряет один уровень: `"\\d"` в строке Python означает `\d`. Слои складываются: скрипт Python внутри
   `bash -c "..."`, запущенного из Windows, уполовинивает слеши дважды.
4. **`wsl -- <команда>` разбирает команду ещё раз** в оболочке Linux по умолчанию: см.
   [Команда, запущенная в WSL из Git Bash или PowerShell, приходит искажённой](calling-wsl-from-windows-shells.ru.md).

## Рецепт

1. **Пишите код инструментом для файлов, а не через оболочку**: редактором, инструментами записи и правки файлов
   у агента или скриптом, который копирует файл. ИИ-агент в Windows не должен записывать текст с `\` через свой
   инструмент Git Bash, даже с `<<'EOF'`.
2. **Если без оболочки не обойтись, держите текст вне командной строки.** Положите скрипт в файл и запустите
   `bash script.sh`; внутри используйте heredoc в кавычках, `printf '%s\n' "$text"` и `read -r`:

   ```bash
   # В файле скрипта: текст копируется байт в байт.
   cat > test.cpp <<'EOF'
   CHECK(getExchangesByPattern("\\d") == "0123456789");
   EOF
   ```

3. **Из программы Windows передавайте Git Bash файл, а не текст скрипта**: `subprocess.run(["bash", "script.sh"])`.
4. **В Python берите сырые строки или читайте текст из файла**: `r"\\d"` сохраняет оба слеша.
5. **В `sed` не подставляйте текст в замену**; возьмите инструмент для файлов или скрипт с буквальной заменой
   (`str.replace` в Python).
6. **Пишите пути Windows с прямыми слешами** (`C:/x/y`): их понимают программы Windows, Git Bash и `wslpath`.
7. **Проверяйте записанный файл**: `grep -n '\\' file` показывает все строки со слешем; сверьте их с исходником до
   сборки.

## Как тестировать

Каждая строка показывает, во что превратилось `if (c == '\\') re("\\d");`; проверено в Windows 11, Git for
Windows 2.55 (bash 5.3), PowerShell 7.6, WSL 3.0.3 с Ubuntu 24.04 (bash 5.2, GNU sed 4.9). Строки bash запускайте
из файла скрипта, а не из командной строки, иначе первая причина заслонит остальные.

| Где | Результат |
|---|---|
| PowerShell: `& bash.exe -c "printf '[%s]\n' 'A\\B'"` (Git Bash) | `[A\B]` |
| PowerShell: `& bash.exe -c '…' x 'A\\B'` (аргумент без пробелов) | `[A\\B]` |
| PowerShell: `& bash.exe -c '…' x 'A\\B C'` (аргумент с пробелом) | `[A\B C]` |
| Python: `subprocess.run([bash, "-c", '…', "x", r"A\\B C"])` (Git Bash) | `[A\B C]` |
| PowerShell: `wsl -d Ubuntu-24.04 -e bash -c "printf '[%s]\n' 'A\\B'"` | `[A\\B]` |
| bash: `cat <<EOF` | `if (c == '\') re("\d");` |
| bash: `cat <<'EOF'` | `if (c == '\\') re("\\d");` |
| bash: `echo -e "$src"`, `printf "$src"` | `if (c == '\') re("\d");` |
| bash: `printf '%s' "$src"` | `if (c == '\\') re("\\d");` |
| bash: `read line` / `read -r line` | `'\'`, `"\d"` / без изменений |
| bash: `sed "s/X/$src/"` | `if (c == '\') re("\d");` |
| bash: `wslpath C:\x\y` / `wslpath 'C:\x\y'` | `C:xy` / `/mnt/c/x/y` |
| g++ 13 на `c == '\'` / на `"\d"` | `error: missing terminating ' character` / `warning: unknown escape sequence: '\d'` |

## Чек-лист для ревью

- [ ] Файлы с `\` (литералы C/C++, регулярные выражения, пути Windows, JSON) записаны инструментом для файлов, а не
      через оболочку.
- [ ] Ни одна программа Windows не передаёт Git Bash текст скрипта с `\` как `bash -c "..."`.
- [ ] Heredoc с кодом использует разделитель в кавычках (`<<'EOF'`) и лежит в файле скрипта.
- [ ] У `read` есть `-r`; текст идёт через `printf '%s'`, а не через `echo -e` или формат `printf`.
- [ ] Каждая строка со `\` в записанном файле сверена с исходником.

## Где встречалось

- **C++ SDK в Windows**: ИИ-агент дописал тест через свой инструмент Git Bash командой `cat >> test.cpp <<'EOF'`;
  `"\\d"` пришло как `"\d"`, и компилятор лишь предупредил. Исходник, который правил скрипт Python, переданный тем
  же путём, получил `'\'` вместо `'\\'` и перестал собираться. Обе строки исправлены инструментом правки файлов
  агента.

## Открытые вопросы

- Правило среды MSYS2 наблюдалось, а не прочитано в её исходниках: `\\` → `\` внутри аргумента в кавычках, `\\`
  без изменений в аргументе без кавычек. Следуют ли правилам Microsoft цепочки из трёх слешей и слеш перед `"`, не
  проверялось.
